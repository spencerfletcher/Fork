### Inferences

- Strongest portfolio assets are already substantive: transactionally consistent snapshot versioning, real stale-write protection, a pure diff engine, loss-preserving parsing, and detailed accessibility-focused tests. The next impressive demonstration is a coherent reliable user journey built on these, not another isolated technical feature.
- Search matching an ingredient removed from the current recipe can surprise a cook. Specify whether search means current ingredients, saved-version ingredients, or history, then test that contract. Do not label this a proven bug without that product decision.
- A recipe-level favorite can change beneath a user. Version-pinned saves and clear “newer version available” behavior align unusually well with Fork's existing model.

### Gaps

- Production commit/build identity, deployment reason, authenticated runtime flows, real mobile hardware, screen reader, offline behavior, production mail delivery, field performance and all tests' present pass status remain unverified. No current-user research or usage telemetry was discovered in this bounded audit.
- No automated accessibility score or WCAG conformance claim is justified by this source inspection. Existing test files are evidence of intended coverage, not evidence they currently pass.

## Which core UX improvements and release gates should come next?

### Takeaway

Prioritize trust and everyday completeness: recover writing, publish intentionally, find a saved recipe, cook from it comfortably, and take the cookbook elsewhere. Preserve the established warm visual language while testing actual tasks on realistic recipes; a full redesign is not established as necessary.

### Cited Findings

- **Writing is guarded but not durably recoverable:** beforeNavigate confirmation and failed-save draft echo protect several paths, but component-only draft state cannot establish recovery after tab/process loss. Stale-save copy explicitly tells the user to reload and reapply edits. — [RecipeForm](../../../src/lib/components/recipes/RecipeForm.svelte), [edit action](../../../src/routes/recipes/[slug]/edit/+page.server.ts).
- **Publication is currently explicit in the form but defaults on:** “Make this recipe public” says it applies to every version. Fork inserts its copy immediately using source visibility before redirecting to edit. This is the present public-default product behavior, **not evidence of an authorization bypass**. A private-first roadmap should change the default and make publication meaning understandable before saving. — [form](../../../src/lib/components/recipes/RecipeForm.svelte), [new baseline](../../../src/routes/recipes/new/+page.svelte), [fork action](../../../src/routes/recipes/[slug]/+page.server.ts).
- **Private-image guarantee needs verification:** uploader obtains a public Storage URL. Do not infer an exploitable leak from this alone; inspect bucket/access policy and test intended private-media behavior before promising private cookbooks or adding household sharing. No hosted storage policy was queried. — [image uploader](../../../src/lib/server/images.ts).
- **Recovery/lifecycle needs design:** delete action hard-deletes recipe and cascading versions, but no delete control is present in inspected edit page. History is append-only during editing, yet that does not make the overall cookbook recoverable after deletion. Add archive/trash/restore semantics deliberately when exposing lifecycle controls. — [delete action](../../../src/routes/recipes/[slug]/edit/+page.server.ts), [edit page](../../../src/routes/recipes/[slug]/edit/+page.svelte), [schema](../../../src/lib/server/db/schema.ts).
- **Existing accessibility work should be preserved:** source includes native checkbox row controls, 44px touch sizing, skip navigation, focus recovery, reduced-motion handling, forced-colors variants, labeled validation and keyboard tag selection; e2e invariant tests inspect targets, overflow, focus rings, forced colors and phone input font sizes. — [invariants tests](../../../e2e/invariants.test.ts), [authenticated tests](../../../e2e/authenticated.test.ts), [layout](../../../src/routes/+layout.svelte), [form](../../../src/lib/components/recipes/RecipeForm.svelte).
- **Empty/error states are not a blank slate:** favorite emptiness differs from filtered-no-results; search offers recovery actions; missing/private recipe and server error copy offer routes onward. — [favorites](../../../src/routes/favorites/+page.svelte), [search](../../../src/routes/search/+page.svelte), [errors](../../../src/routes/+error.svelte).
- **Multi-language input limitation is concrete:** slugify removes characters outside ASCII word characters; the old roadmap documents empty/colliding non-Latin tag slugs. The implementation still contains that expression. — [helper](../../../src/lib/helpers.ts), [roadmap](../../history/2026-10-milestones.md).

### Inferences

Recommended order and **proposed acceptance targets**, not industry benchmarks or fixed dates:

1. **Writing and privacy trust.** Durable draft recovery and private-first creation/forking, clear saved/saving/offline status, safe conflict recovery, reset/resend mail usability, ownership/privacy test matrix and backup/restore drill. Routine release hygiene should record the just-updated build and reconcile docs; the residual homepage observation is only a follow-up check, not a confirmed defect or main product priority. The user has already deployed; do not schedule that deployment again as unfinished work. Gate: no lost text in scripted validation failure, connection interruption, refresh, tab close/reopen, session expiry and stale-tab scenarios; conflict preserves both saved and unsaved work; no silent publish; logged-out/other-user access fails for every private surface. Photos need an explicitly tested recovery/privacy contract too.
2. **An excellent personal cookbook.** Clarify Cookbook versus Discover rather than making the same route change meaning. Put owned, adapted and saved recipes in a coherent library, filterable by ownership/source and collections; preserve quick tags and favorites. Add private notes and pin saved versions; visibly distinguish bookmarking from making an editable adaptation. Search within one's cookbook, sort/filter, paginate growing collections. Gate: in moderated tests, at least 4 of 5 representative cooks independently save, organize and retrieve a chosen recipe without explaining the navigation; test with 100–500 varied recipes, not only seed cards. This small sample is qualitative, not statistical proof.
3. **Editor/content completeness.** Keep the efficient paste-first input; add grouping for sauce/dough/filling, yield quantity+unit independent from servings, optional equipment and total/rest time, original-source attribution, preview and restore-as-new-version. Bring the entire typed-content/readers/diff/fixtures slice forward together. Gate: paste a real multi-component recipe, correct it, save/reopen/compare without losing structure or wording; unparsed data remains visible; preview and saved rendering agree; no browser keyboard obstruction at 320–430px and tablet widths.
4. **Capture and ownership.** Print readable recipes; export documented human-readable recipes plus machine-readable snapshots and attribution; then deterministic URL import into reviewable editor, followed by migration from common recipe managers and OCR when needed. Export should not depend on importing first. Gate: export→import round-trip retains declared fields/history/provenance; supported URL corpus measures field accuracy and gracefully exposes missing/ambiguous fields; original stays available; no import publishes automatically.
5. **Cooking reliability and convenience.** Verify existing local cook mode, wake lock, scaling and tick persistence on physical iOS/Android/tablet; add reliable timers, unit/temperature display and ingredient access from steps. Offline read of intentionally saved recipes precedes speculative native rebuild. Gate: actual meal cooked on a counter without losing place or accidental changes, quantities/ranges/scaled grams consistent, unscaled text identified; multiple timers recover from background/resume with correct elapsed time; denied wake lock and offline limitations explained. A timer should use wall-clock deadlines and persisted state appropriate to its promises, not rely solely on component-local setTimeout.
6. **Differentiation through cooking memory.** Add private “Made it” log keyed to exact version and multiplier, note/photo, then turn an intentional tweak into new version or fork. This can be a thin core milestone, not a social-platform prerequisite. Gate: cook twice, answer “what did I make last time and what should I change?” from the record; recipe edits never rewrite the past cook.

Shared UX gate: representative long/no-photo/multi-section recipes; keyboard-only completion; logical heading/focus order; 200% zoom and narrow reflow; visible touch/focus states; non-color-only change cues; Safari/Chrome/Firefox; loading, empty, error, denied permission and slow-network states. Require measured performance budgets after establishing a baseline, rather than invented current numbers. Test the cooking state on real hardware, not only screenshots.

### Gaps

- Grouping, library naming, draft sync scope, archive policy, favorite pin update behavior and first export format are product proposals needing focused design, not decisions already made. Multi-device draft sync may follow local recovery if one-device safety meets the initial use case; explicitly tell the user which is supported.
- Units need culinary correctness work: metric/US/imperial volume and food density are different problems; do not claim the existing gram table makes full conversion trivial. Resting/chilling and cooking temperatures do not scale mechanically with servings.

### Inferences

- Competitive features and recurring requests deserve serious consideration; reject/defer for a stated reason such as workflow dependency, operational burden, unproven demand in Fork's target audience, safety/correctness or solo-maintainer capacity. Absence of a version-control angle alone is not a reason to omit a good cookbook feature.
